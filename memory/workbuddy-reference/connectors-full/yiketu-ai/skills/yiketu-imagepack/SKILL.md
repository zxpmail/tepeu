# 易可图商品套图

## 1. 目标与规则优先级

根据用户提供的商品图片和自然语言要求，调用易可图 MCP 创建商品套图任务、查询真实结果并交付图片。

执行时遵循以下优先级：

1. **用户明确要求决定业务目标**：平台、市场、语言、分辨率、图片类型、数量、比例和具体要求不得擅自修改。
2. **运行时 MCP `inputSchema` 决定参数是否合法**：类型、required、enum、数量范围、长度限制、字段结构均以当前 Schema 为准。
3. **本 Skill 决定业务参数如何组织**：包括是否传可选字段、智能组图/自主选图、同类图片如何分组、重试和交付方式。
4. **业务事实必须有真实来源**：商品属性、点数、价格、折扣、任务状态、成功数量等不得自行推测或估算。
5. MCP description 或示例中的示范值只用于理解接口，**不得直接当成用户任务的默认值或真实业务数据**。

数组必须传原生数组，不得自行增加 `{item: ...}` 等包装结构。

---

## 2. 标准执行流程

正常流程：

```text
理解用户需求
→ 确认商品图片
→ 获取易可图 MCP 工具
→ 非易可图 OSS 图片：获取 STS 后立即上传
→ 整理商品事实与用户要求
→ 选择智能组图或自主选图
→ 创建商品套图任务
→ 获取 taskId
→ 按 MCP 规定时间查询任务
→ 核验实际生成结果
→ 交付图片 + taskId
```

优先使用准确工具名称：

- `mcp__易可图__getOssStsToken`
- `mcp__易可图__saveAiProductImgPackTask`
- `mcp__易可图__getAiProductImgPackTaskList`

一次模糊搜索未命中时，应先用准确工具名称再次查找，不得直接判断 MCP 未连接并要求用户重新配置。

## 3. 参数缺省与组图模式

### 分辨率

用户明确指定 1K / 2K / 4K 时严格遵循。

用户未指定时：

**不传 `resolution`。**

不得因为 MCP 示例或效果考虑自行默认 2K / 4K。

### 平台

用户明确平台时按用户要求传入，具体枚举以运行时 Schema 为准。

不要根据语言推断平台。

当前服务端未传平台时存在默认平台行为，因此：

- 只生成白底图、纯视觉场景图等平台影响较小的图片时，可继续执行；
- 生成完整套图、卖点图、详情图等明显受平台版式影响的内容，而用户未指定平台时，应先简短确认平台；
- 不得自行把“未指定平台”解释为用户选择 Amazon。

### 市场 / 站点

只有用户明确指定时才传。

例如“Amazon 美国站”可传对应美国市场；“Amazon + 中文”不能推断为美国站。

**语言和市场是两个独立维度。**

### 语言

用户明确指定语言时严格遵循，具体枚举以运行时 Schema 为准。

如果用户要求完整套图、卖点图、详情图等可能包含文字的图片，但未指定语言，应在创建付费任务前简短确认语言。

如果用户已说“亚马逊的，中文”，则平台和语言已经明确，不得再追问图片数量、类型或分辨率。

### 智能组图

用户已提供商品图片，并表达“生成一套商品图 / 上架图 / 完整套图”等需求，但**没有指定具体图片类型和数量**时：

**直接使用智能组图。**

图片类型、数量、分辨率缺失都不是阻断条件；分辨率未指定时直接不传。

### 自主选图

用户明确指定图片类型、数量、比例或某类图片特殊要求时，使用自主选图，并严格遵循用户要求。

如果用户指定了图片类型但没指定数量，采用合理最小数量，默认每类 1 张。

## 4. `resultImgParamList` 强制分组规则

自主选图时：

**同一 `resultImgType` + 同一 `resultImgRatio` 的多张图片，必须合并为一个条目，并把 `resultImgCount` 设为该组总张数。**

例如用户要求 5 张 1:1 场景图：

```json
[
  {
    "resultImgType": "scene_img",
    "resultImgRatio": "1:1",
    "resultImgCount": 5,
    "resultImgDesc": "生成5张不同场景图，覆盖多个合理使用环境，保持商品主体和外观一致。"
  }
]
```

**禁止**拆成多个相同 `scene_img`、相同比例、`count=1` 的条目。

只有以下情况才拆分条目：

- `resultImgType` 不同；
- `resultImgRatio` 不同。

同类型同比例的多张图即使希望覆盖不同场景、卖点或角度，也应把这些要求合并写入同一个 `resultImgDesc`，不得为了每张图单独写描述而拆条目。

## 5. 业务事实与商品事实

所有对用户有实际影响的事实信息，都必须有明确来源，**没有来源就不要补全**。

可信来源仅包括：

1. 用户明确提供的信息；
2. 当前 MCP / 易可图接口真实返回的信息；
3. 当前上下文中已明确提供的易可图官方规则或数据；
4. 商品图片中可以直接观察到的视觉事实（仅限商品外观类信息）。

### 商品事实

可以使用：

- 用户明确提供的商品资料；
- 图片中明确可见的颜色、造型、结构、接口、按键等。

仅凭图片不得自行确认：

- 材质、成分比例；
- 防水、可机洗、保暖等级；
- 尺寸、容量、承重；
- 功率、续航、兼容型号；
- 安全认证、质量等级。

`productDesc` 只写商品本身，优先级为：

```text
用户提供的商品资料
> 用户明确描述
> 图片中可确认的视觉事实
```

创意场景可以合理发挥，但不得把创意场景反写成商品属性。

### 点数、价格与折扣

点数、价格、折扣、单张成本、预计消耗、节省金额等都属于**业务事实**。

只有在以下情况才能向用户说明具体数字：

- 当前 MCP / 接口明确返回；
- 用户明确提供；
- 当前上下文中存在明确的易可图官方计费规则。

如果没有真实来源：

**不得估算、推算或编造具体点数和价格。**

禁止根据以下方式自行计算：

- 图片张数 × 假定单价；
- 分辨率推算价格；
- 图片类型推算价格；
- 所谓“标准价”“常规价”“通常每张 X 点”；
- 其他任务、其他产品或历史经验类比；
- 自行假定批量折扣、活动价或优惠。

例如没有真实计费数据时，不得说：

> 10 点/张  
> 11 张约 110 点  
> 改成 3 张可以省 80 点

如果用户询问“这次要扣多少点”“减少图片能省多少点”，但当前没有可靠计费信息，应直接说明：

> 当前 MCP 没有提供本次任务的具体点数消耗，无法准确计算或估算。

可以按用户要求修改图片数量，但不得用未经证实的点数数字作为建议依据。

### 任务事实

任务状态、图片总数、失败数量、taskId 等必须以 MCP 实际返回为准。

不得自行猜测未返回的任务事实或实际扣点数量。

## 6. OSS 上传、付费任务与重试

非易可图 OSS 图片必须先上传到易可图 OSS。

`getOssStsToken` 返回短时凭证，因此：

**获取 STS 后立即上传。**

不要在获取 STS 后再进行：

- 多轮分析；
- 写多份临时脚本或中间文件；
- 无关工具调用；
- 外部 URL 验证；
- 第三方图床上传。

严格按照当前 MCP 上传说明使用 host、dir、policy、signature、token、callback、MIME 和 fullPath。

不要修改 OSS 域名，也不要因为私有 OSS 地址外部打不开就判断上传失败。

### 上传失败

如遇 `Policy expired` / `SecurityTokenExpired`：

1. 重新获取一次最新 STS；
2. 立即重试上传一次；
3. 仍失败则停止。

不得循环取凭证和反复测试。

### 参数错误

如 MCP 返回参数结构、Schema 或反序列化错误：

1. 对照当前运行时 `inputSchema` 修正；
2. 最多正常重试一次；
3. 仍失败则停止。

### 点数不足

如果 MCP 明确返回点数不足：

- 立即停止；
- 告知用户当前账号点数不足；
- 不自行推算“还差多少点”或“本次原本要扣多少点”。

不得擅自降低分辨率、减少图片数量、修改图片类型或重复提交。

### 付费任务控制

生成任务可能消耗用户账号点数。

本 Skill 负责避免未经用户同意重复创建任务，**不负责在没有真实计费数据时估算具体点数消耗**。

未经用户同意，不得：

- 重复创建可能收费的任务；
- 为了“更完整”自动增加大量图片；
- 为了修复部分失败自动再次生成；
- 用虚构的点数节省金额诱导用户修改方案。

## 7. 任务查询与结果验收

创建任务成功并获得 taskId 后，按照 `getAiProductImgPackTaskList` 当前工具说明规定的首次等待时间和轮询间隔查询，不高频轮询。

**不能只根据 `status="success"` 判断整单成功。**

必须同时检查：

- `imgNum`
- `imgFailNum`
- `resultImageList` 实际数量

只有满足：

```text
imgFailNum = 0
且
resultImageList 数量 = imgNum
```

才可以表述为“全部生成成功”。

如果 `imgFailNum > 0` 或实际返回图片数少于 `imgNum`，则属于部分成功，应明确告诉用户计划数量、成功数量和失败数量。

部分失败时先交付已成功结果，不得未经用户同意自动重新创建付费任务。

交付前，如果图片包含文字，应检查明显的：

- 乱码；
- 拼写错误；
- 文案残缺；
- 与用户指定语言不一致。

发现明显文字问题时应如实提示，不得称其为完全正常，也不得擅自重新生成收费任务。

## 8. 用户沟通与禁止行为

正常执行保持简洁。

不要向普通用户展示：

- STS；
- OSS Key；
- signature / token；
- curl 或上传命令；
- MCP Schema；
- 参数序列化和内部调试过程。

但应让用户知道：

- 真正缺少且无法继续的信息；
- 任务创建失败；
- 点数不足；
- 部分生成失败；
- 最终生成结果；
- **taskId**。

任务创建成功后可告知一次 taskId；最终交付时必须附带 taskId，方便用户追溯。

### 不要过度询问

如果用户信息已经足够执行，就直接执行。

例如用户说“亚马逊的，中文”，且已提供商品图：

- 平台 = Amazon；
- 语言 = 中文；
- 未指定类型和数量 → 直接智能组图；
- 未指定分辨率 → 不传。

不要再追问“几张、什么类型、1K 还是 2K”。

### 计费问题的回复

如果用户询问具体点数或价格，而当前没有真实计费数据：

- 明确说明当前无法准确计算；
- 不给出猜测数字；
- 不使用“约”“大概”“通常”包装未经证实的价格。

### 禁止行为

禁止：

1. 虚构商品材质、性能、尺寸、认证等事实；
2. 虚构或估算没有真实来源的点数、价格、折扣和节省金额；
3. 未经用户要求提高分辨率或增加图片数量；
4. 根据语言擅自推断市场；
5. 用户未指定平台时自行认定 Amazon；
6. 同类型同比例多图拆成多个 `count=1` 条目；
7. 获取 STS 后进行多轮无关操作；
8. 使用第三方图床绕过易可图 OSS；
9. 参数或上传失败后无限调试；
10. 一次工具搜索失败就判断 MCP 未连接；
11. 点数不足后偷偷修改方案重试；
12. 未经用户同意重复创建收费任务；
13. 只看 `status=success` 就宣称全部成功；
14. 有明显文字错误却仍称结果完全正常；
15. 未取得真实结果时声称图片已经生成完成。

## 核心原则

**用户要求决定目标。**

**MCP Schema 决定参数是否合法。**

**Skill 决定业务如何组织。**

**业务事实必须有真实来源。**

**商品属性、点数、价格、折扣、任务状态都不得脑补。**

**同类型同比例多图必须合并为 `count=N`。**

**未指定类型和数量时优先智能组图。**

**STS 获取后立即上传。**

**失败不无限调试。**

**部分成功不冒充全部成功。**

**taskId 必须可追溯。**
