# DxC 内容审校

内部调用 DxC CLI 时只使用 PATH 中的全局入口：`dxc <参数>`。本 Skill 的版本是 `0.3.24`，
安装流程必须已经验证 `dxc version --json`、本 Skill 集和该版本完全一致。正常任务不得通过 npm、
npx 或其他包执行器解析 DxC，也不得硬编码任何用户的可执行文件绝对路径。若 `dxc` 不在 PATH，或
CLI 报告官方 Skill 版本不一致，停止并请用户按安装说明重新安装同一指定版本；不在当前任务内联网
解析、切换版本或改用仓库源码。

DxC 的调用由本 Skill 给出。每次只直接执行当前 Skill 明确写出的一个 DxC 命令，不寻找或猜测替代命令。只把 CLI 上一次结构化结果中的 `workItemId` 或 `choiceId` 作为不可解释也不可编辑的字段直接交给下一次结构化调用；字段传递不得经过模型重新生成或自然语言转录。禁止手工复制、拼接、改写、截取、解码、重建、落盘、持久化或转存这些值，也不要求用户接触它们。

调用仍在运行时，`DXC_BROWSER_EVENT` 只表示需要立即承载当前页面，不表示命令失败或完成。等到进程退出并收到唯一的 `DXC_RESULT` 最终帧后，先把其中完整结构化结果作为当前事实保存，再向用户转述；不得用进度文案、浏览器地址或自己概括的字段替代最终工作项。

禁止用 Python、Shell、PowerShell 临时脚本、循环、管道、命令替换、后台任务、并发或定时器包装 DxC 命令。禁止调用 CLI help，禁止查看源码、日志、内部文件或解析返回值内部结构来推断下一步。没有明确的下一步时，停在这里，如实告诉用户当前还不能继续。

CLI 失败时，若当前 Skill 明确规定了 CLI 返回选项、用户选择后继续的分支，只按该分支等待并提交用户选择。
其余失败禁止再次调用、轮询、跳阶段、重新进入阶段或创建替代项目。只转述其中面向用户的 `message` 和唯一 `recovery` 所表达的安全方向，隐藏命令、内部标识、本地位置和诊断细节，然后停止；不得自行执行恢复动作或推测根因。

若宿主无法把完整结构化字段直接传给下一次调用，停止并说明交接能力不足；不得为了继续而手抄或重建引用。
状态目录权限被拒绝时，用户的自然语言同意不改变沙箱。只有宿主实际授予目标目录权限后才能继续；
不要反复在相同受限环境执行，也不要修改全局安全配置、放宽目录权限或搬迁文章。doctor 的工作目录检查不代表文章状态目录可写。

面向用户只展示审校结论和确实需要回答的问题，不展示命令、内部标识、本地位置或实现过程。

接到当前工作项时，使用其随附的当前阶段资料和写作区；不要另行查找项目文件、画像、记忆、知识库、日志或源码。完成审校后，只执行一次 `dxc workflow advance --work-item <当前工作项> --json`，并把返回的新工作项交回总控。

工作项随附的创作记忆中，`enforce` 是必须核对的约束，`guide` 是审校参考，`suggest` 只作候选且不得因未采用而阻断；保留 `principle`、`judgment`、`expression` 等真实类型含义。

执行前完整阅读[审校清单](references/review-checklist.md)。核对研究证据、结构、正文、标题与视觉的一致性；没有阻断项时写入 `verdict: pass`，存在阻断项时写入 `verdict: block`，并说明具体问题和安全修复动作。只把真实交付风险写成阻断项，不为了推进弱化问题。
从完整流程正常到达时，正文的逐项去 AI 味独立循环已经是正文阶段完成门，不能等到本阶段才首次执行。本阶段仍直接阅读当前原始资料，对事实、承诺、结构、标题、视觉和交付一致性做完整复核；若发现正文后来修改造成新的 AI 味或整体回归，也必须阻断并返修，但不重复或伪造正文阶段的逐项回执。用户显式从本阶段进入时，不假定也不声称正文独立门已经执行；直接审完整成品，缺失必要证据或发现明显问题就阻断。
直接使用工作项实际提供的上游材料，输入是否必需由 CLI 合同决定。可选材料未提供时，只说明
哪些对照未执行，不能仅因缺文件写 Blocker，也不能声称前序已通过。若正文确有无来源数据、
论证缺口或标题承诺落空，仍按具体位置和缺失依据阻断。

用户在本阶段明确指出可迁移到未来文章的审校偏好或拒绝原因时，另执行一次 `dxc memory signals record --automatic --project <随工作项收到的 projectId> --action <user-feedback|user-rejection|user-edit|user-choice> --summary <只描述用户行为的最小摘要> --json`。普通通过、单篇事实问题和 Agent 自己的审校意见不记录；返回 `recorded: false` 时不提示、不重试。该独立动作不推进阶段。

CLI 返回返修选择时，只向用户展示它给出的可读选项。用户选定后，执行一次 `dxc workflow advance --work-item <当前工作项> --choice <所选 choiceId> --json`，把返回的新工作项交回总控。不要自己判断阶段、调用 `start --from`、解析 choiceId，或直接修改其他阶段产物。

CLI 要求展示通过的审校结论时，展示后等待用户决定：采用则执行一次 `dxc workflow advance --work-item <当前工作项> --confirm --json`；不采用则停下。用户指出仍需返修时，把审校结论改为 `verdict: block` 并写明问题，再执行一次不带确认的推进。出现无法继续的结果时，如实说明并停下，不自行重试或转到其他阶段。

审校通过后的推进结果若包含 `learning`，它只是八阶段之外的本地生命周期回执：`knowledge: indexed|unchanged` 表示当前完成稿已幂等进入本地知识库，`pending` 表示文章完成不回滚但索引待修复；`semantic: pending` 表示正文真值和关键词索引仍已保留。`authorSignals: disabled|not-due` 不需要呈现；`review-due` 且带有 `candidate` 时，只把其中跨项目摘要和历史文章证据当成候选，核对方向一致、适用范围和明显反例后，最多向用户提出一个长期规律问题，不展示内部 ID。它不代表规律已经成立或生效。

用户决定候选后，把原始 `candidate` 和用户决定交给[创作记忆 Skill](../dxc-memory/SKILL.md)执行其完整的升级或拒绝命令；暂不决定则不写。然后继续使用审校推进已经返回的下一工作项。不得静默升级，也不得把确认问题改成第九步。

用户明确要求从审校开始新建文章时，执行一次 `dxc workflow start --title <用户主题> --from quality-review --json`；已有文章只在用户从项目总览中明确选定后，把项目总览结构化结果中的 `projectId` 原样传递给一次 `dxc workflow start --project <项目总览返回的 projectId> --from quality-review --json`。不得从文章标题猜测或重建；上下文丢失时，重新读取项目总览并让用户选择。随后仍只使用返回的当前工作项。

内容审校通过只证明本阶段有证据的内容结论，不能写成“没有交付阻断项”。分别说明内容审校、实际模板
HTML 容量、当前预览查看以及外部草稿创建/回读的证据；尚未执行的环节明确为未验收。
核对正文、摘要及视觉兑现已采用标题的承诺；母稿工作标题允许保留，发布装配会在派生副本中同步
与其相同的首个文档 H1，不为机械改标题要求正文返修。已提供实际预览时再核对其中的最终标题，
尚无预览不能声称已验证装配。视觉引用使用当前合同的章节绑定。用户另行要求导出时，
须核对实际文内图片嵌入和目标应用能否解析；复制图片文件不能代替嵌入。不要覆盖同名但用途不同的文件。
