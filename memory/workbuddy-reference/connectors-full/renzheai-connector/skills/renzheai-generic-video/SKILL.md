# 通用视频

**什么时候轮到它**：用户要做的东西在技能清单里找不到对应品类——比如婚礼跟拍、
活动纪实、游戏实况、旅行 vlog……这些都还没有专门的方法论。

⛔ **轮到它的前提是「用户已经亲口选了它」**，不是「你判不出来」。判不出品类时先问用户
（候选 = 各个品类 + 一条「都不是，按通用框架做」），用户选了那一条才走这份细则。
蒙一个品类往下做，用户要么当场否掉，要么更糟：看不出哪里不对但就是不满意。

**它不是「什么都能做」的万能条目**：只要清单里有对得上的具体品类，那一条永远优先。
它存在的意义是「用户看完清单说都不是」时仍有一套完整框架可走，
而不是给你一个绕开具体方法论、也绕开那一次提问的借口。

## 各环节细则去哪看

**这张表是唯一的指引** —— 文件名由本品类自己定，读之前照这里对，不要凭约定猜。
需要哪个环节就读哪一份（都在本目录下）：

| 环节 | 文件 | 谁在什么时候读 |
| --- | --- | --- |
| 访谈与落库参数 | `interview.md` | 访谈环节：建项目 / 建下一集，开口问之前 |
| 编剧 | `script.md` | 剧本师：动笔之前 |
| 分镜 | `storyboard.md` | 分镜师：动笔之前 |
| 素材 | `asset.md` | 素材师：动手之前 |

## 落库字段这样填

- `story_mode`：**一律 `anthology`**（各条内容互相独立、不承接）——通用框架不假设有连续叙事
- `finale_style`：`closed`（每一条都自成闭环、有明确落点）；用户明确要开放式留白才传 `open`
- `is_finale`：**恒 `false`**（anthology 下必须为 false）

⚠️ 这三项**不要问用户**——问了也解释不清，用户要的是「做条片子」不是理解字段。
直接按上面填，复述里也不出现这几行。

## 落地之后

发现某一类需求反复走到这里（比如一个月里十几次都在做婚礼跟拍），
那就是**该给它建一个专门品类**的信号——在后台新建一个 skill 即可，不用发版。
反复出现「用户选了都不是」本身就是产品信号，别让它沉在日志里。
