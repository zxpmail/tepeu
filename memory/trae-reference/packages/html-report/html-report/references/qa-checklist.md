# Final QA Checklist

Run this checklist after the report, required opening Intro, local assets, and
optional features are complete. Static QA is the default delivery gate. It
checks the report package without opening or controlling a browser.

## 1. Default Execution Boundary

- Do not invoke browser-control tools or browser plugins for report generation
  or QA.
- Do not open, navigate, inspect, or control the user's browser, tabs, history,
  profile, cookies, or logged-in session.
- Do not start local HTTP, capture screenshots, or inspect browser console and
  network state merely because a report was created, updated, restyled, or is
  ready for delivery.
- A report request does not imply permission for rendered browser validation.
- Rendered QA is optional and may run only when the user explicitly requests it
  for the current report. Use an isolated test browser for that separate check.
  Never reuse or control the user's existing browser or session for report QA.
- When rendered QA was not explicitly requested, record it as `NOT RUN`, not
  `BLOCKED` or `FAIL`.

## 2. Blocking Static Technical Checks

- The HTML starts with `<!-- Generated by Trae Work -->` and includes a doctype,
  charset, and viewport declaration.
- All report paths are relative; there are no CDN URLs, absolute local paths, or
  base64 blobs for normal assets.
- Every referenced local CSS, JavaScript, font, image, and diagram file exists
  inside the delivered report directory.
- HTML IDs are unique. Every internal link, citation target, `aria-controls`, and
  source-reference target resolves to an existing ID.
- A report-like deliverable contains one opening Intro with the page's single
  `h1`. `contained` and `integrated` include a one- or two-sentence HTML summary
  that states the main conclusion. A `stage` either includes that summary or is
  immediately followed by `main > section#report-overview` whose heading is
  immediately followed by `.report-overview__summary` before evidence. Email
  templates, resumes, standalone
  visualizations, and dense operational dashboards may use their native opening
  pattern instead.
- The Intro uses at most one layout modifier: no modifier means `contained`, and
  `.report-intro--integrated` and `.report-intro--stage` never appear together.
  `.report-intro--with-media` and `.report-intro--plain` remain independent
  media/presentation states rather than layout modes.
- A generic no-image Intro defaults to `contained` and has no image request or
  placeholder. Every Intro keeps its title, required summary, and any subtitle,
  metadata, or highlights as real HTML.
- Every source URL is validly formed and long URLs or IDs have source-level wrap
  rules. User-provided sources without URLs use plain source labels.
- Available deterministic syntax or contract validators for the generated HTML,
  CSS, and JavaScript pass. A validator failure blocks delivery; the absence of
  browser tooling does not.
- Run `node <skill-dir>/scripts/validate-report-source.mjs <report.html>`; this
  local source-only gate rejects a restrictive `max-width` or `max-inline-size`
  on an unscoped global `p` selector without rendering the report.
- `scripts/validate-skill-contract.mjs` validates this Skill package, not a generated report. Its `PASS` must not be presented as generated-report QA.

Any failure in this section blocks delivery.

## 3. Static Visual And Contract Review

- Unless the user explicitly selected another visual language, the source
  follows `report-default-v1`; apply the Design Style rules in the HTML rather
  than copying them into the plan.
- The selected palette follows explicit user/brand direction, otherwise an
  accepted Hero, and only without a Hero uses prompt/content cues. It is injected
  once and keeps page colors separate from chart/data colors.
- With an accepted Hero and no explicit override, the `Color preset` cue records
  the resolved visual cue.
- This trace is a static decision-record check only; it does not add browser or
  rendered palette harmony QA. Actual harmony remains `NOT RUN`.
- Page surfaces remain neutral. Chart/data colors do not become card or section
  fills.
- When a plan exists, it records exactly one compact Intro selection line:
  `Intro mode: <contained|integrated|stage> — cue: <content/material cue>`.
- The opening uses full-width `header.report-intro`, a mode-ready
  `.report-intro__surface`, and an ordered `.report-intro__content` layer while
  the body remains on its centered reading grid.
- A `contained` Intro is the compatible default and may use
  `--page-brand-soft` or `--page-surface-muted` on its bounded surface.
- An `integrated` Intro has `.report-intro--with-media`, qualified local media
  covering its surface, declared desktop and mobile focal positions, a text-safe
  area, and a functional scrim derived from `--page-*` tokens. Its text and
  summary remain real HTML and do not depend on the image.
- A `stage` uses `block-size: auto` and the bounded
  `min-block-size: clamp(36rem, 88svh, 58rem)`, not a fixed viewport height. Its
  source resets the minimum to content height under
  `(max-height: 600px) and (orientation: landscape)`, print, and forced-colors,
  and disables Intro motion or scroll effects under `prefers-reduced-motion`.
  It may remain typographic without `.report-intro--with-media`.
- Long titles, text zoom, localization, and narrow layouts can increase Intro
  height naturally; source rules do not clip required copy or force the title
  onto one line.
- When the image-free Intro uses CSS accents, there are no more than two. They
  are non-informational pseudo-elements outside normal flow, use only page
  tokens, remain behind the HTML content, and add no image or SVG asset. They
  use no gradient, shadow, or animation and are suppressed by
  `.report-intro--plain`, `.report-intro--with-media`,
  `.report-intro--integrated`, and `.report-intro--stage`. Their absence is not
  a failure.
- The source keeps long-form documents prose/table-led and gives every admitted
  chart a distinct analytical question and nearby interpretation.
- No more than two analytical charts, diagrams, or evidence images appear in
  sequence without prose synthesis, interpretation, or a section conclusion.
- Heading tokens, font declarations, radii, spacing, and container treatments are
  consistent. Content containers do not use accent top/left/full borders, border
  gradients, or decorative color strips.
- Each card, metric, callout, tag, and icon has a clear information role. Cards
  are not nested.
- Responsive CSS collapses multi-column layouts, protects long labels and URLs,
  and provides a non-scroll-dependent treatment for core tables.
- Every chart, diagram, table, and meaningful image has a title or caption.

Apply `references/visual-badcase-gates.md`. Source-checkable V0 failures block
delivery. Geometry, clipping, rendered contrast, chart marks, and actual mobile
readability are not proven by static review. Record Intro crop, real-pixel
contrast, first-screen whitespace, and desktop/mobile composition as `NOT RUN`
instead of claiming that they passed.

## 4. Conditional Static Feature Checks

Run only the sections that match the report.

### Quantitative Charts

- ECharts is loaded from the report's local `_shared/js/` directory and chart
  code lives in `assets/charts.js`.
- Every chart container ID or selector referenced by JavaScript exists in the
  HTML, declares a non-zero `height` or `min-height`, and has visible fallback
  markup or code for empty data.
- The local ECharts library script appears before `assets/charts.js`, and chart
  initialization runs only after its referenced DOM container exists.
- All charts derive colors from the same active chart palette.
- Configuration includes `renderer: 'svg'`, `animation: false`, tooltip setup,
  and resize handling.
- Labels, legends, data arrays, null handling, and displayed source values are
  internally consistent.
- Do not claim that marks, tooltips, labels, or resize behavior rendered correctly
  unless optional rendered QA was explicitly requested and completed.

### Structural Diagrams

- Diagram source and every generated local asset exist in the delivered report.
- The chosen Mermaid, Graphviz, PlantUML, HTML/CSS, or justified SVG approach
  matches the diagram's complexity.
- Node and connector labels are present in source, and detailed image diagrams
  include the required caption and any planned zoom implementation.
- Do not claim rendered node readability or connector clarity from static checks.

### Conditional Intro Media And Additional Images

- For one explicitly named film or media work, product, or brand, a silent text-
  only Intro fails. Confirm either a suitable user-
  provided or first-party Hero asset, or the valid fallback after an explicit no-
  image request or bounded source, access, download, quality, crop, or contrast
  failure; do not add the lookup narrative to the report body.
- Record exactly one compact delivery result outside the report body:
  `Intro media: USED — <owner/source>` or `Intro media: FALLBACK — <short reason>`.
- Accepted Intro media comes from a user-provided or first-party official source,
  is saved locally, and records its owner, source page, and access date.
- Decorative Intro media uses `alt=""` and `aria-hidden="true"`. Evidence-bearing
  images appear in the report body with meaningful alt text and a visible caption.
- Image dimensions, paths, desktop/mobile focal positions, text-safe area, and
  fallback behavior are declared. Missing, corrupt, watermarked, or unsourced
  media is removed. An `integrated` Intro then removes both
  `.report-intro--integrated` and `.report-intro--with-media` and becomes
  `contained`; a `stage` may remove `.report-intro--with-media` and remain a
  typographic stage.
- Rejected, removed, replaced, or fallback media invalidates any Hero-led
  palette; re-resolve it from replacement media or the no-Hero content cue.
- Lightbox code exists only when zoom materially improves inspection.
- Cropping, rendered contrast, focal-point usefulness, first-screen balance, and
  viewport readability remain `NOT RUN` without explicitly requested rendered
  QA.

### Interactive Reports

- Navigation, mode-switch, resize, and linkage controls have matching source
  targets and semantic control markup.
- JavaScript contains safe missing-target handling, and responsive/focus styles
  exist for the primary controls.
- Apply the static self-check in `references/interactive-prd.md`.
- Do not claim runtime navigation, scrolling, keyboard focus, or mode switching
  passed without explicitly requested rendered QA.

## 5. Optional Rendered QA — Explicit Request Only

This section is outside the default report workflow. Run it only when the user
explicitly requests rendered testing for the current report.

1. Use an isolated test browser. Never attach to or control the user's existing
   browser, tabs, profile, cookies, history, or authenticated session.
2. Serve the report directory over local HTTP inside the isolated test setup.
3. Render the complete page at desktop `1440 x 900` and mobile `390 x 844`.
4. Capture and inspect a full-page screenshot at both widths when screenshots are
   part of the requested acceptance check.
5. Check report-caused console errors, failed local resources, document-level
   overflow, and each requested primary interactive state.
6. Record rendered QA separately from static QA. If isolated browser tooling is
   unavailable, report only the optional rendered check as blocked; do not
   retroactively fail a completed static QA unless the user made rendered testing
   an explicit acceptance criterion.

## 6. Delivery Gate

Record a concise `PASS` or `FAIL` for static package structure, local resources,
source integrity, citations, opening Intro, and each used optional feature. Record
rendered QA as `NOT RUN` by default.

Deliver the complete report directory when every blocking static item passes.
When a report contains charts, complex responsive layouts, or interactions,
state plainly that their rendered and runtime behavior was not browser-verified
unless the optional rendered check was explicitly requested and completed.
