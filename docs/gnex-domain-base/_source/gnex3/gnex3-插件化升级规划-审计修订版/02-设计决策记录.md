## 一、P0 级决策

### D-P0-01 跨进程工具管线裁决（审计 P0-01）

- **发现**：sandbox-seam/policy 宿主 sandbox-runtime 进程，却 listen agent-service 进程的 `tools/pre-execute` waterfall；跨进程同步裁决语义无定义，裁决链路无法落地。
- **设计思考**：gnex2.0 现实架构中 SandboxEnforcer 在 gnex-agent-sdk（agent-service 侧），sandbox-runtime 经 `/internal/sandbox/ensure` REST 被调用——**裁决与执行本来就分属两进程**。工具管线是 agent-service 的进程内总线，跨进程参与 waterfall 同步语义不可行；正确映射是"裁决在管线侧、执行在运行时侧"。
- **决策**：**采用方案①（裁决器同构部署进 agent-service）**，并明确三角色分工：
  - `gnex3-cap-sandbox`（seam Definition）：只定义 `SandboxPort`/`sandboxPolicy` 契约（放 libs/gnex-sandbox，宿主=被引用的契约库，不 listen 管线）；
  - `gnex3-cap-sandbox-policy`（裁决器）：**宿主改为 agent-service**，提供 `sandboxPolicy` 服务，作为管线 guard（SandboxEnforcer 位置）在 agent-service 进程内裁决（读会话模式/档位/网络策略），批准后经 `SandboxPort.ensure`（既有 REST `/internal/sandbox/ensure`）请求 sandbox-runtime 执行；
  - `gnex3-cap-sandbox-backends`/`-pool`（执行平面）：宿主 sandbox-runtime 不变，只做执行。
- **修订落点**：05 §4 管线图（标注裁决器在 agent-service、执行在 sandbox-runtime）；sandbox-policy spec 宿主改 agent-service、§3.3 改为"作为管线 guard 注册（非 listen 跨进程事件）"；sandbox-seam spec §3.3 删除 listen 声明、改为"契约库+执行端口"；04 目录宿主列订正。

### D-P0-02 类名现状/设计混淆（审计 P0-02）

- **发现**：ent-tenant/ha 的 9 个类名（TenantInterceptor/PgRlsInitializer/WorkerRegistry 等）在 gnex2.0 源码零命中（来自设计文档），spec 表述为"对标 GNEX2.0 模块"。
- **设计思考**：O5 要求现状以源码为准；设计文档类名应明确标注来源，避免验收基线错位。
- **决策**：spec §2 映射列**拆分两栏**：`代码实证来源`（源码类名+路径）与`设计规格来源`（设计文档类名，标注"设计态/待落地"）；§6 验收加"前置条件"说明（先落代码基线）。
- **修订落点**：ent-tenant/ent-ha spec §2 重构；04 目录对应行加"设计态"标注。

### D-P0-03 验收命令与测试类零匹配（审计 P0-03）

- **发现**：ent-api `-Dtest=GatewayTest` 与七个 Gateway*Test 零匹配；内核域 3 份精确类名不匹配；client-modules `*Ui*` 疑似空匹配。
- **设计思考**：验收命令是 CI 假绿风险源；通配或显式类名列表可消除。
- **决策**：统一 `-Dtest=<前缀>*Test` 通配形式（覆盖 V1-Vn 全部类）；跨模块测试归属修正（MCP V6 移 agent-service；client 用 vitest 命令）；测试类命名与 V 断言一一对应（`<插件>Test` 内方法名 = Vn）。
- **修订落点**：ent-api、kernel 域 3 份、client-modules、tool-mcp 等 spec §6 命令修正。

### D-P1-04 三类设计缺口
- **决策 a（双端一致性测试）**：内核 spec §6 增 `KernelDshAlignmentTest` 套——同场景在 dsh(TS) 与 cordis-jvm 各跑断言同结果（装载序/卸载回卷/waterfall deny/scope 隔离），作为"与 dsh 对齐"的落地验证。
- **决策 b（Spring 桥时序）**：内核 spec §3.3 明确：@PluginService 全部 lazy + ObjectProvider 注入；PluginRuntime 在 `ApplicationContextInitializer` 阶段启动（先于业务 Bean 依赖）；卸载时桥代理 invalidate（后续调用抛明确异常）；插件服务接口纯接口（禁 Spring 注解）；事务只在 Spring Provider 侧开启。§6 增 SpringBridgeTest 扩展（卸载后调用/并发装载/循环依赖/事务边界）。
- **决策 c（集群清单 skew）**：06 S4 固化"清单随镜像不可变"为 ADR 建议；副本启动上报 assembly digest 到 observability；S4 多副本回归增"混合插件集期间 P0 断言仍成立"用例。
- **修订落点**：kernel spec、06、05（测试方案附录已含）。

### D-P1-05 loop 与 fail-closed 矛盾
- **决策**：tools-registry §5 明确 guard 序两级语义：**mandatory**（缺失→deny fail-closed：approval/permission/sandbox-policy/tenant/gate 相关 guard）与 **optional**（缺失→跳过+观测告警：loop 检测器——它是成本保护非安全边界）；tools-loop §7 改为与 registry 一致（缺失=跳过+告警，不再"其余照常"模糊表述）。
- **修订落点**：tools-registry/tools-loop spec。

### D-P1-06 wrapper 顺序与工具级重试
- **决策**：05 §4 补 wrapper 顺序图：**timeout（最外）→ spill → 本体**；v3.0 **不做工具级自动重试**（重试语义归 model-retry，LLM 请求级；工具调用失败由循环重发+幂等设计兜底），tools-timeout 只管超时，删除"重试归 retry 插件"的推诿表述；MARK_ONLY 删除。
- **修订落点**：05 §4、tools-timeout/tools-registry spec。

### D-P1-07 guard 归属
- **决策**：四个 guard（SandboxEnforcer/PathInspector/RiskInspector/SecurityInspector）**并入 gnex3-cap-tools 作为内置 guard 实现**（配置化启停、顺序固定），approval/permission 为独立插件（mandatory）；tools-registry §3.3 补内置 guard 契约。
- **修订落点**：tools-registry spec §3.3/§4；04 目录 tools-registry 行注"含内置 guard 集"。

### D-P1-08 证据词汇统一
- **决策**：05/gate spec 定义统一写证据契约 `writeEvidence { paths: string[], hash: string, turnId: string, ts: number }`；tool-fs（turnWritePaths）、tool-str-replace（writeEvidence）、tool-http（evidence）三份 spec 改为引用同一契约；发布时机统一为"工具成功后由工具发布（emit write-evidence），gate 消费"。
- **修订落点**：05 §4、gate/fs/str-replace/http spec。

### D-P1-09 ask_user 超时冲突

### D-P1-10 MCP 跨服务管线

### D-P1-11 双头归属

### D-P1-12 内核线程模型
- **决策**：kernel spec 增 §3.4 线程模型：① ctx 服务注册表 `ConcurrentHashMap` + volatile 发布；② 事件分发：emit 异步（虚拟线程池 per-listener 隔离，异常不影响主流程）、waterfall 同步（调度线程执行 + `waterfall-timeout` 5s 熔断）；③ fiber 生命周期：装载/卸载互斥锁 + 状态机（LOADING/RUNNING/STOPPING/STOPPED）；④ 装卸竞态：卸载等待在飞调用（引用计数 + drain），在飞调用结束后才回卷。
- **修订落点**：kernel spec（新增 §3.4 + 对应验收 V8-V10）。
