## 1. 项目背景与目标

### 1.1 现状痛点（用户陈述）

GNEX 2.0 是服务化的（9 个微服务 + 共享库），**修改起来非常麻烦，因为不是插件化的、不解耦**：改一个能力要动服务内部代码、跨服务耦合、重新构建部署。

### 1.2 目标

| # | 目标 | 衡量 |
|---|------|------|
| G1 | GNEX 保持**服务化**部署形态（微服务、副本、弹性伸缩、租户隔离、企业记忆 SoR 全保留） | 服务边界与 k8s 部署形态不退化 |
| G2 | 每个服务**内部由插件组合完成**：服务 = 插件运行时 + 插件集；能力 = 插件 | 新增/替换能力不动服务骨架 |
| G3 | 学习 dsh 已被验证的插件化机制与规制（ctx/服务容器、inject/provide、事件、realm、工具注册表、preset、双平面归属规则） | 新架构的接口关系可对齐 dsh 的 53 个核心接口服务 |
| G4 | 形成可工程执行的 **SDD Spec 体系**（遵循 GNEX v2 SDD 纪律：spec 5 要素、contracts、验收断言） | specs/ 下每个插件一份可验收 spec |

### 1.3 非目标（明确不做）

- ❌ 不换语言/不换 Spring 技术栈（仍 Java 21 + Spring Boot 4.x）
- ❌ 不引入 OSGi / 不把 Spring 换成 Cordis JS
- ❌ 不把"完成证据门、审批地板、租户边界、记忆 SoR"做成可卸载插件（继承 ADR-046「闸门不可卸」）
- ❌ 不允许 Agent 自我修改内核（企业红灯，继承既有裁决）
- ❌ 本次只做**设计与 Spec**，不做代码实现（后续工程化按 Spec 实施）

## 2. 继承的既有约束（必须尊重，不可推翻）

来源：`gnex-core-v2/docs/v3.0/运行时/Agent-OS设计尺子.md`（0.34）、`外部对标-*裁剪.md`、`memory/decisions-log.md`（ADR-044/046/049-053）。

| 约束 | 内容 | 对 3.0 插件化的影响 |
|------|------|---------------------|
| C1 | **三条尺子**：原语清晰、可靠性内建、观测能拆开故障 | 插件化不得掩盖故障模式；插件接口必须让每步可观测 |
| C2 | **P0 硬约束**：完成证据门（P0-a）、企业记忆平面（P0-b）、审批地板、租户边界 | 这些能力在 3.0 中是**平台核心插件**（平台持有、管理面可配、运行时不可由租户/Agent 卸载） |
| C3 | **闸门不可卸**（ADR-046）：完成催促、Inspector DENY/审批、Task 重入、高危确认等 | 插件框架必须支持**受保护插件**（protected）机制：装卸权限仅平台管理员，且关键闸门插件默认加载、拒绝卸载 |
| C4 | 企业禁止 Agent 自挂/自卸插件（self-modification 红灯） | 插件管理面（安装/卸载/配置）只暴露给管理员与运维，不暴露给 Agent 工具 |
| C5 | 多副本/弹性/HA 是服务级属性 | 插件化在**服务内部**发生；跨服务通信仍走既有 REST/Bus/RPC；副本与弹性在服务编排层（k8s）不动 |
| C6 | 既有"无纳入"裁决（ADR-044 等）针对**换内核** | 本次不换内核，是**服务内部组合层插件化**；是对既有裁决的工程演进而非推翻红线 |

> 📌 补充指令（用户第二轮）：**以当前实际代码为准，不过分参考 docs/v3.0 设计文档**（v3.0 尚未实现，现在是 gnex2.0 版本）。本规划全部现状描述基于源码分析（9 服务逐包 find/read/grep + pom 依赖矩阵 + `_work/gnex-services-analysis.md` 1331 行服务深析）；docs/v3.0 中的目标态（企业记忆三平面 SoR、状态面异步物化、三层恢复等）一律标注「设计态/目标态」，不作为已实现事实；SDD 规格中的 gnex2.0 对标全部指向真实类名与端点；P0-a/P0-b/E 红线按既有审计/ADR 继承为约束而非现状声明。

## 5. 关键设计原则（先行确立）

1. **服务是部署单元，插件是组合单元**：9 个服务保留；每个服务内部引入"插件运行时（Java 版 cordis 语义内核）"，插件按服务装配（服务 = 内核 + 插件集 + 装配清单）。
2. **dsh 已验证的规制直接映射**：ctx 服务容器 → 服务内 `Ctx`；inject/provide → 依赖声明；waterfall/emit 事件 → 事件总线（服务内进程内 + 跨服务走既有 Bus）；realm/scope → 租户/项目/会话作用域；tool 注册表 + 管线 → 工具插件注册表 + Inspector 链融合；agent preset → 会话级 Agent 组合；profile/bundle 组合 → 服务级插件装配清单（Java 版）。
3. **企业特性不进插件热路径**：多副本、弹性、租户边界、记忆 SoR 保持平台层；闸门类插件受保护（protected）。
4. **先接口后实现**：所有插件先定 contracts（对齐 `libs/gnex-contracts` 纪律），再写实现。
5. **可观测优先**：插件生命周期事件（install/start/stop/uninstall）进可观测面，故障可拆到插件级。

## 6. 风险与开放问题

| # | 风险/问题 | 应对 |
|---|-----------|------|
| R1 | Java 动态插件装载（类加载/依赖冲突）风险 | 倾向"代码/模块级组合 + 服务重启生效"的准插件化（先于 jar 热装）；热装作为后续阶段 |
| R2 | 插件框架引入的复杂度 vs 收益 | 先做最小内核（ctx/inject/provide/事件/生命周期），用 2-3 个试点服务验证后再铺开 |
| R3 | 与既有 Spring DI/InspectorChain/Bus 的关系 | 融合而非替代：Spring 管服务装配，插件内核管服务内能力组合；Inspector 链作为安全插件保留 |
| R4 | SDD 体系规模（30-60 个插件 spec） | 模板化 + 分批并行编写；先核心后叶子 |
| R5 | 既有"无纳入"裁决的评审争议 | 本文档 §2 已声明继承红线、不换内核；必要时出对比说明 |
| Q1 | 插件粒度：服务内插件 vs 跨服务插件 | 初判：按能力域插件化，一个插件可被多个服务装配 |
| Q2 | 热装 vs 冷装 | 初判：v3.0 先冷装（重启生效），热装（HMR 类比）列为 v3.1 |
| Q3 | dsh JS 插件桥（D8）优先级 | 初判：非主线，做可行性论证 + 原型，不与核心插件化并行排期 |
