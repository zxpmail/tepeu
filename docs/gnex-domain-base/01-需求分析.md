# 需求分析

> 产品名：gnex 领域应用基座（下文称基座）。
> 设计约束来自 `docs/gnex-domain-base/_source/gnex3/` 审计修订版，重点是融合设计、插件目录 L4、接口关系、租户规格。
> 编号是后文规格的唯一需求出处。正文自含，读本文件就能知道要做什么。

## 1. 要解决的问题

gnex3 负责把智能体规划、调度、跑起来，并守住企业红线：租户硬隔离、认证、组织、审批、审计、记忆、完成证据。它不负责「一类业务系统长什么样」。

请假、巡检、资产、工单，这些系统各自有人、菜单、页面、单据、服务和校验。若每个系统从头写一套，集群应用无法复用，智能体也无法按同一套语义去配置。

基座是这些业务系统的统一抽象。业务系统在基座上组合：应用包 + 数据实体 + 标准页面 + 业务服务 + 语义说明 + 必要的业务钩子。智能体可以提议组装，人在生产环境点头后才落地。

## 2. 谁用

| 角色 | 要做成的事 |
|---|---|
| 平台管理员 | 开通租户内的基座、登记数据源、安装应用包 |
| 应用管理员 | 管一个应用的成员、角色、发布和停用 |
| 业务用户 | 打开已发布应用，按权限看列表、填表、提交 |
| 组装智能体 | 读语义包，提议页面、实体和绑定；不直写库 |
| 业务开发 | 用应用包和命令钩子加规则，而不是改基座内核 |

## 3. 不做什么

- 不签发登录、不自建第二套用户库、不替代 gnex 租户硬过滤。
- 不重做智能体循环、模型网关、沙箱、技能、企业记忆。
- 不做某一行业的成品（制造、零售、政务包都不在本轮）。
- 不提供任意 SQL 窗口。
- 不在首版做跨源大查询引擎、移动端专用壳、页面内任意脚本。

## 4. 功能需求

状态列：首版必做。来源列只作索引。

### 4.1 身份与权限（消费 gnex，不另起炉灶）

| 编号 | 需求 | 来源 |
|---|---|---|
| FR-IDN-01 | 每个请求携带 gnex 发出的令牌。令牌里要有租户、用户、项目。缺任一项就拒绝，不默认放行 | gnex 租户规格：缺失即拒绝 |
| FR-IDN-02 | 基座记录「这个用户是不是这个应用的成员」。组织角色不等于应用成员 | D-002 |
| FR-IDN-03 | 应用角色是一组权限点。权限点写成 `应用.实体.动作` | 设计 |
| FR-IDN-04 | 数据权限包含三件事：能不能做这个动作、行过滤条件、哪些字段要打码。查询时三者同时生效 | 设计 |
| FR-IDN-05 | 路径里不放租户段。查找只按令牌中的租户。请求的路径、查询或正文里若另带租户且与令牌不一致，拒绝，并且不返回对象 | gnex 串租户为 P0 |
| FR-IDN-06 | 成员和角色变更要形成审计记录，并投递到 gnex 审计。投递失败进外发队列，不能只记在内存 | gnex `audit` 服务 |

### 4.2 应用与路由

| 编号 | 需求 | 来源 |
|---|---|---|
| FR-APP-01 | 应用有稳定键、显示名、状态、所属租户、版本。租户内应用键唯一 | 设计 |
| FR-APP-02 | 状态只能是草稿、已发布、已停用、已退役。不允许从已退役回到已发布 | 设计 |
| FR-APP-03 | 路由把应用内路径指到一个页面。同一应用内路径唯一 | 设计 |
| FR-APP-04 | 菜单由已发布路由生成，不另存一套菜单 | D-013 |
| FR-APP-05 | 已停用应用的路径返回停用，不能落到别的应用页面 | 设计 |
| FR-APP-06 | 未发布的路由对业务用户不可见，对应用管理员可见 | 设计 |

### 4.3 业务服务

| 编号 | 需求 | 来源 |
|---|---|---|
| FR-SVC-01 | 业务服务有键、版本、协议、地址引用、健康状态 | Backstage 目录只借「登记与健康」，不借它的单租户部署 |
| FR-SVC-02 | 基座服务键必须以 `biz.` 开头，不得占用 gnex 进程内服务名 | D-014 |
| FR-SVC-03 | 应用绑定的是某一服务版本。换版本留下绑定历史 | 设计 |
| FR-SVC-04 | 健康为不可用时，调用返回降级码和原因，不返回空成功 | 设计 |
| FR-SVC-05 | 连接用的密钥只保存引用号 | D-012 |

### 4.4 可组合界面

| 编号 | 需求 | 来源 |
|---|---|---|
| FR-UI-01 | 页面是一份模式：布局、区块、数据绑定、动作。保存前先校验 | D-004 |
| FR-UI-02 | 首版区块至少有：表格、表单、详情、筛选条、统计卡、空态 | 设计 |
| FR-UI-03 | 外壳提供租户名、应用切换、菜单、无权限提示。外壳不画业务字段 | 设计 |
| FR-UI-04 | 模式校验失败时整页不渲染，并给出字段级错误 | 设计 |
| FR-UI-05 | 区块取数只走统一查询，模式里不写连接串 | D-012 |
| FR-UI-06 | 模式与渲染器分开。首版只交付一个官方渲染器 | D-004 |

### 4.5 统一数据

| 编号 | 需求 | 来源 |
|---|---|---|
| FR-DAT-01 | 数据源登记类型、连接引用、所属租户、最近一次探测结果 | 设计 |
| FR-DAT-02 | 首版能登记 PostgreSQL、MySQL、REST 三种源 | D-010 |
| FR-DAT-03 | 业务实体描述字段、类型、是否必填、对应到哪个源的哪张表或哪个接口 | Frappe 的单据类型只作类比：元数据驱动，不引入其 Python 运行时 |
| FR-DAT-04 | 托管实体由基座建表。外接实体只做映射，不改源库表结构。外接源整份只属于登记它的租户。源上没有租户列时，不拼接租户条件 | 设计 |
| FR-DAT-05 | 统一查询支持过滤、排序、分页，并尽量下推到源 | Hasura 连接器「能下推就下推」 |
| FR-DAT-06 | 跨源拼接若估算行数超过上限，拒绝并返回明确原因 | D-016 |
| FR-DAT-07 | 托管查询必须同时带上令牌中的租户和项目，调用方不能关掉。外接源按 FR-DAT-04：有租户列才下推该列，没有则靠数据源登记隔离 | gnex 租户硬过滤，并补上项目 |
| FR-DAT-08 | 写入使用实体命令（新增、修改、删除）。不接受任意 SQL 文本 | 设计 |

### 4.6 语义与智能组装

| 编号 | 需求 | 来源 |
|---|---|---|
| FR-SEM-01 | 语义包用版本化文档说明：有哪些实体、能做什么动作、有哪些约束、页面该怎么提示 | D-006 |
| FR-SEM-02 | 智能体不能直接写元数据表，只能提交组装事务 | D-007 |
| FR-SEM-03 | 组装事务状态：已提议、已校验、待审批、已应用、已回滚 | 设计 |
| FR-SEM-04 | 对已发布应用的落地，必须先经 gnex 审批。审批未通过不得写正式版本 | gnex 审批原语 |
| FR-SEM-05 | 草稿应用落地可免审批，但必须审计 | 设计 |
| FR-SEM-06 | 语义包里出现词表以外的类型或动作，整单拒绝，不猜测 | 设计 |

### 4.7 应用包

| 编号 | 需求 | 来源 |
|---|---|---|
| FR-PKG-01 | 应用包清单包含应用、实体、页面、服务绑定、语义包、迁移步骤 | Odoo 模块清单的「依赖 + 数据文件 + 钩子」结构，改成 JSON 清单 |
| FR-PKG-02 | 安装要么全部成功，要么回到安装前。不允许留下半张表、半个菜单 | 设计 |
| FR-PKG-03 | 升级按版本顺序执行迁移，禁止跳版 | 设计 |
| FR-PKG-04 | 依赖的包或服务未安装时，拒绝安装并指出缺哪一项 | 设计 |
| FR-PKG-05 | 业务规则通过已登记的 HTTP 钩子加入，地址是一个 `biz.` 服务。钩子拒绝则返回业务拒绝码，不写半截数据。首版不在基座进程里加载业务 jar | D-018 |

## 5. 非功能需求

| 编号 | 要求 | 度量 |
|---|---|---|
| NFR-01 | 串租户、串项目 | 隔离测试里，用租户 A 读到租户 B 的行，或用项目 P1 读到同租户项目 P2 的行，成功次数都是 0 |
| NFR-02 | 页面模式读取 | 缓存命中时，单租户 p95 ≤ 80 毫秒 |
| NFR-03 | 安装时长 | 标准包（1 实体、1 列表、1 表单、无外接源）≤ 60 秒 |
| NFR-04 | 审计不丢 | 元数据写入 100% 有投递尝试；失败进入外发队列并产生告警 |
| NFR-05 | 故障隔离 | 基座进程停止后，已在 gnex 内运行的智能体循环仍能完成本轮工具调用（不访问基座的那些） |
| NFR-06 | 密钥 | 清单、日志、页面模式、错误信息中不出现密钥原文 |
| NFR-07 | 语言 | 首版外壳、错误提示、标准区块标题为中文 |
| NFR-08 | 副本 | 基座不把会话存在本机内存。多副本共用同一 PostgreSQL |

## 6. 一套业务系统如何长出来

1. 平台管理员登记数据源（或使用基座托管库）。
2. 安装应用包。包声明实体、页面、服务和语义。
3. 安装事务建表或映射、写入路由、发布语义包版本。
4. 应用管理员把人和角色放进应用。
5. 业务用户从外壳进入路由，区块经统一查询读写实体。
6. 需要改页面时，智能体提交组装事务；已发布应用等审批后应用。
7. 行业规则放在该应用的命令钩子里，不放进基座内核。

## 7. 验收怎么算需求被覆盖

每条 FR 至少被一条规格验收引用。规格验收必须能回指到某条 FR 或某条决策。对账表在 `03-场景与流程设计/90-场景功能对账.md` 和 `specs/00-trace.md`。
